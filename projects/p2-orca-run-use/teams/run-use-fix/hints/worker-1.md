# worker-1 へのヒント

## 方向

- 調査ファイル（charter の「出発点」）の「直す案」1〜6 は、完了条件 1〜6 とほぼ 1 対 1 に対応している。案を土台にして、SKILL.md の B・C・D を書き換えるのが早い。案から変えた所があれば、どこをなぜ変えたかを報告に書く。
- 事実の根拠は調査ファイルの「確認した事実」だけ。SKILL.md に書く Orca の挙動は、そこにある事実か、自分で読むだけのコマンド（`inbox`・`run-show`・`run-list`・`terminal show`・`terminal list`）で確かめたことだけにする。
- 調査ファイルの「まだ確かめていないこと」（`read` がいつ 1 になるか・`--limit` 無しの件数・結んでいない端末から `task-create` が通るか）は、事実として書かない。手順がそれに依存する所は「未確認」と書くか、依存しない形にする（例: 未処理の判定は `read` だけに頼らず `check` で確かめる、など。形は任せる）。
- 古い記述は消さずに「2026-10-22 時点では〜」と併記する（完了条件 1）。特に D の「`check` は `run-use` 無しで通る（2026-09-17 確認）」と、B の「新しい端末は最初に `run-use`」。
- 戻りの入口（完了条件 3）は、3 つの分岐それぞれに、そのまま打てる 1 行のコマンドを置く。分岐の判定に使うフィールド（`coordinator_handle`・`connected` など）も書く。

## 気をつけてほしい点

- B・C・D 以外（A・E・F など）にも `run-use` や「新しい端末は結び直す」の趣旨が残っていたら、SKILL.md の中なら合わせて直してよい。報告で触れる。
- job 固有の値（`run_31ab…` などの Run ID、「2 時間」、`run-use-log.md`、`consumer_generation` の具体値）は dev-tools に書かない。時間は「親 repo が決める」と書く（完了条件 6）。例のプレースホルダは `<run_id>` の形で。
- 変えるのは SKILL.md と `ticket-template.md` の 2 つだけ。`worker-instructions.md` など他のファイルに直すべき所を見つけたら、直さずに報告の申し送りに書く。
- SKILL.md の中のコマンドは 1 行。`orca` は `&&`・`|` でつながない単独の形（JSON の絞り込みが要るなら「出力の◯◯を見る」と文で書く）。
- Orca で打ってよいのは読むだけのコマンドだけ。`run-use`・`check`・`send`・`task-create`・`worker-start` は打たない。
- review_request の本文に、完了条件 1〜7 ごとの「どこを直したか（SKILL.md の節・行）」と、1 の対応表（直した箇所 → 調査ファイルの事実）、`git -C <dev-tools> status` と `git -C <dev-tools> diff --stat` の出力を入れる。レビュアーはそれを根拠に照合する。
