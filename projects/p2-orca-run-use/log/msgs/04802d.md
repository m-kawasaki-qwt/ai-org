判定: 2・4・6・7 は満たしている。1・3・5 に足りない所がある（重い順に 4 件）。

1. **【条件 5】自分が依頼していない戻りの扱いが行き詰まる（SKILL.md 138 行目）。** 「`check` で受けて処理し（`--ack` まで）」の後に「依頼元のセッションがまだ生きているなら、そのセッションが処理する」とあり、どちらが処理するのかがぶつかっている。新しい決まりの下でこれが起きる典型は「A が依頼 → 後で B が別の依頼のために `run-use` → A の戻りが B に届く」で、このとき A は生きている。B が「A が処理する」と読んで手を出さないと、A は D の入口で通知先 B が生きているのを見て分岐 3（触らない）に入る。しかも A の `check` は `consumer_fenced` で弾かれる（調査「確認した事実」5）。結果、誰も `--ack` せず、同じ通知が B に流し込まれ続ける（調査の案 5 が避けたかったこと）。「起票ファイルが手元に無いときは body は読むだけ」も、`--ack` するのかが読めない。末尾の「報告が要るかをユーザーに聞く」も、案 5 の「1 行だけ伝える」より往復が増える。
   → 通す形: 通知先になっている端末（＝届いた側）が必ず `--ack` まで処理する、と 1 本に決める。起票ファイルが読めれば「戻り」へ転記し、読めなければ body の要点をユーザーへ 1 行で渡す。「依頼元が処理する」の文は消す（依頼元に処理させたいなら、依頼元が分岐 2・3 の `run-use` で引き取る、と D の分岐側に書く）。

2. **【条件 3】`inbox` の入口で未処理を取りこぼすおそれがある（108 行目の `--limit 20`、C の 99 行目「件数が多くて埋もれるときは `--limit` で絞る」）。** `orca orchestration inbox --help` で見ると、絞り込みは `--limit`・`--terminal`・`--full` だけで、種類や未読では絞れない。新しい順に返り、heartbeat も同じ列に並ぶ（2026-10-23 に `inbox --limit 30 --json` を打ったら 30 件中 20 件が heartbeat）。依頼先が動いている間は heartbeat が 1 分おきに積まれる（調査「まだ確かめていないこと」3）ので、20 件だと数十分より前の `worker_done` が画面から落ちる。C の「`--limit` で絞る」は向きが逆で、絞るほど古い未処理が落ちる。
   → 通す形: 20 で固定しない。「最後に処理した時刻より前まで届く件数にする（足りなければ増やして打ち直す）」と書き、出力を `run_id`・`type`（`worker_done`・`question`・`escalation`）・`read` で見る、とする。C の文も同じ向きに直す。`--limit` 無しの件数が未確認なのは、今の書き方のままでよい。

3. **【条件 3】分岐 2 に「通知先が無い（`coordinator_handle` が `null`）」が入っていない（125〜128 行目）。** `orca orchestration run-list --json` を見ると、今ある Run の半分以上で `coordinator_handle` が `null`。このときは `orca terminal show --terminal <handle>` を打てないので、今の分岐の書き方では、どこへ進むかが決まらない。（`terminal show` の `connected` という項目名は、2026-10-23 に実物で確かめた。合っている。）
   → 通す形: 分岐 2 の条件に「`coordinator_handle` が `null`」を足す（`terminal show` は打たずに分岐 2 へ）。

4. **【条件 1】D のコードブロックから `orca orchestration check --run <run_id> --peek --format --json` の行を消している（旧 97 行目）。** 条件 1 は「古い記述は消さず、2026-10-22 時点では〜と併記」。139 行目の箇条書きで旧記述に触れてはいるが、コマンドの行そのものは無くなっている。
   → 通す形: その行を残し、「2026-10-22 時点では、通知先が自分のときだけ通る（結び付いていない端末では `consumer_fenced`）」と添える。139 行目の箇条書きを指す形でもよい。
