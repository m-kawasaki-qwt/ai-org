# ヒント: worker-1（リーダーから）

## 受け手から逆算する

4 つのファイルは、別チーム（org-build）が「職種 UI デザイナーの規範」と「画面で確かめる基準」に**要約して写し、番号で参照する**元になる。だから:

- **番号を先に決めて、4 ファイルで同じ番号を使う。** 例: sources は領域の接頭辞＋連番（`H-01` ヒューリスティクス、`A-01` アクセシビリティ、`V-01` 視覚の階層、`P-01` 段階的開示、`D-01` ダッシュボード、`G-01` データの見せ方、`K-01` ダークモード、`F-01` アフォーダンス、`R-01` レスポンシブ、`W-01` 文章）。checklist は `B-01`（画面を作る前に決めること）／`C-01`（画面を撮って確かめること）。principles は `U-01`。形は任せるが、途中で振り直さない。
- **checklist の 1 項目は 1 行で読める長さ**（問い＋判定の基準＋参照番号）。説明が要るなら sources 側に寄せる。

## チェックリストの作り方の当て

- 「はい／いいえ」で答えられるかは、**p5 の 5 枚のスクリーンショットに実際に当てて**確かめる。答えを出してみて、迷った項目は問いを具体にする（例: 「見やすいか」→「本文の文字と背景のコントラスト比が 4.5:1 以上か」「一覧の 1 セルの文字が折り返して 2 行以上になっていないか」）。当てた結果（5 枚それぞれの はい／いいえ）を checklist か feedback-map に残すと、レビュアーとリーダーが追える。
- 川崎さんの条件（PC 900〜1800px・ダークモード・開いて回らずに要点・全部並べない）は**セオリーの適用条件**として扱い、項目の判定の基準に入れる（例: 「900px と 1800px の両方で撮って、横スクロール・要素の重なりが無いか」）。条件そのものを出典の代わりにしない。
- 「ログを並べただけ」「YAML をそのまま HTML にした」を、一般のセオリーのどこで捕まえられるかを考える（情報の階層・段階的開示・ダッシュボードの「何を判断する画面か」・データインク比 など）。捕まえられないなら feedback-map に「引っかからない」と書き、無理に当てない。

## 出典

- 一次資料優先: Nielsen Norman Group（10 heuristics・progressive disclosure・visual hierarchy など）／W3C WCAG 2.2（1.4.3・1.4.11・2.4.7・2.4.11・2.5.8 などの Understanding ページ）／Tufte（データインク比）／Material Design・Apple HIG（ダークモード）／Stephen Few（ダッシュボード）など。
- 裏取りの印は、どの項目を WebFetch で開いたかが一目で分かる形にする（例: 列に `✅ 開いて確認` / `△ Gemini のみ`）。主要な原則は全部 ✅ にする。
- 書籍で URL が本しか無いものは、著者・出版社のページか、要旨を引用している信頼できるページを URL にし、その旨を書く。

## 気をつけてほしい点

- 量に溺れない。各領域 3〜8 項目で十分。チェックリストに使わない原則を大量に集めない。
- feedback-map は、フィードバックの「画面ごとの指摘」「UI 全体の指摘」の箇条書き 1 つ＝1 行。1 つの箇条に指摘が 2 つ入っているもの（例: 「時系列」の箇条）は分けてよいが、まとめはしない。
- principles は「作るときの手順・考え方」（要素ごとに何のために誰に出すかを決める → 一覧と詳細に振り分ける → …）。checklist と同じ文を並べ直すだけにしない。
