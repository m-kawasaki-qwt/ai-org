## 完了条件ごとの確かめ方と結果

- **2（ペルソナ 3 つ・1 ファイルずつ）**: 3 ファイルあり、32〜38 行。形を揃えた（誰か／何をしに開くか／最初の数秒で掴みたいこと／嫌うこと・離れる理由／判定の問い）。kawasaki は「認知負荷」「全部並べない（10 文字程度・要件の文を一覧に出さない）」「開いて回らずに掴みたい（ギュッと渡し…元の記録まで辿れる）」「明るい画面は嫌（ダークモード）」「PC・900〜1800px」をフィードバックの言葉で入れた。scratchpad の仮 repo で worktree の orgctl を打ち、`assign reviewer --persona kawasaki --persona sales` → CLAUDE.md の 55 行目・98 行目に「# ペルソナ: kawasaki／sales（この目線で見る）」の下に中身が入ることを確認。`--persona nobody` は「使えるペルソナ: end-user, kawasaki, sales」で exit=1。
  - orgctl が「# ペルソナ: <名前>」の見出しを付けるので、ファイル側の先頭は H1 にせず「**目線:** …」の 1 行にした（見出しの二重を避けた）。
- **4（立場とコーディネーターの受け口）**:
  - レビュアー: `review_ok` の前に毎回、自分で撮り（作業者の画像で済ませない）、ペルソナの判定の問いとチェックリストに照らす。通らなければ review_ng。指摘の上限 4 回目でもペルソナの判定が通らないなら承認せず escalate（p5 の「承認 → リーダーが rework」の筋をレビュアーの段で止める）。
  - リーダー: 承認後、PM へ出す前に自分で撮り直して kawasaki で判定。通らなければ rework、レビュアーの見落としを thread に残す。組むときにペルソナを `--persona` で付ける。
  - PM: 子の報告の画像を自分で開いて見てから合格・上へ。文章だけで合格にしない。
  - コーディネーター: 編成案で「画面を作るか」を最初に決め、作るなら UI デザイナーを入れるか・どのペルソナのレビュアー（複数可、ペルソナごとに別のレビュアー）を必ず欄にする。end-user・sales の具体をパックに書く。
  - 撮り方: `screen-check.md` に playwright スキルの参照（`capture-local.mjs`、川崎さん向けは 900・1800 の幅、初期表示は FULL_PAGE なし）と p5 の注意 4 点（サンドボックスの外・scratchpad・npm の `--cache`・`名前,/パス`）。
  - 判定の中身（チェックリスト）は `research/checklist.md` の参照にしてあり、〔後半で確定〕の印を付けた。
- いずれも「画面を作るチームでは」と条件付き。画面の無いチームのシステムプロンプトに増えるのは各立場の節（4〜5 行）だけで、手順の本体は参照先。
