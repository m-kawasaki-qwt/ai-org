# 目的

AI 組織に、ビューアの試走（p5）で足りないと分かった 3 つを足す。目的は、組織が作るものを、川崎さんが見る前に組織の中で「川崎さんに出せる水準か」まで持っていけるようにすること（川崎さんの認知負荷を減らすのが、この組織の目的。ai-org の `policy.md`）。

出発点: 川崎さんのフィードバック `/Users/maka343noshi/ghq/github.com.qwt/m-kawasaki-qwt/job/company/system/ai-org/feedback/2026-10-24-viewer.md`（とくに「組織の側の原因と足すもの」）と、プランの決定ログ（dev-tools の `docs/todo/ai-org-plan.md` の 2026-10-24 の行）。

足すもの:

1. **職種「UI デザイナー」**（`org/occupations/ui-designer/`）: 画面を作る・直すときに、要素ごとに「何のために、誰に出すか」を先に決めてから組み立てる。一般的な UI・UX の原則（要点を先に・詳細は畳む・クリックできるものが分かる・決めた画面幅の範囲で崩れない・色やダークモード・情報の階層・ログを並べるだけにしない 等）を規範に入れる。フィードバックの指摘が、この規範で防げる形になっていること。
2. **ペルソナで見るレビュアー**（`org/personas/` と、`orgctl assign` の `--persona`）: レビュアーに「誰の目線で見るか」を持たせる。最初のペルソナは 3 つ: 川崎さん本人（認知負荷を減らしたい・全部並べない・開いて回らずに掴みたい・明るい画面は嫌）／実際に使うエンドユーザー／営業する側。ペルソナの中身はファイル 1 つずつ。チームコーディネーターが編成案で、どのペルソナのレビュアーを付けるか（複数可）を決める。
3. **「出せる水準か」を実際の画面で確かめる基準**: 画面を作るチームでは、レビュアーとリーダーが Playwright で実際の画面を撮り、ペルソナの目線で「このまま川崎さんに出せるか」を判定する。PM も撮った画面を見てから上へ上げる。根っこのセッション（job）も上へ出す前に同じ基準で見る（org-project-new のスキルに書く）。撮り方（ローカルのポートの待ち受けはサンドボックスの外で動かす 等、p5 で分かったこと）も手順に入れる。

**進め方（2026-10-24 川崎さんの指示）:** 川崎さんはデザイナーではないので、UI デザイナー（UI・UX）の規範と「出せる水準か」の基準は、**一般に良いとされている UI・UX のセオリーを細かく調べて定義するところから始める**。調べるのは Gemini（dev-tools のスキル `gemini-api`。Web 検索を Gemini に任せる CLI `gemini-api`）を使ってよい。定番の原則（例: ユーザビリティのヒューリスティクス・アクセシビリティの指針・情報の階層・ダッシュボードの設計・データの見せ方・ダークモードの配色 など）を、出典つきで集め、そこから規範と判定の基準（チェックリスト）を作る。調べた結果（出典の一覧と要約）はこのプロジェクトのディレクトリに残す。

# 完了条件

0. 調べた UI・UX のセオリーの一覧（出典つき）と、そこから作った判定の基準（チェックリスト）が、このプロジェクトのディレクトリにある。UI デザイナーの規範と画面で確かめる基準は、これを元にしている。
1. 上の 3 つが、雛形（`org/occupations/`・`org/personas/`・`org/positions/`・`org/context.yaml`・コーディネーターの規範）と `orgctl` に入っていて、`orgctl assign ... --persona <名前>` でペルソナがレビュアーのシステムプロンプトに入る。存在しないペルソナを指定したら、分かる言葉で止まる。
2. フィードバックの指摘（画面ごとの指摘・UI 全体の指摘）の一つ一つについて、足したもののどこでそれを防げるかの対応表がある（報告に書く。防げないものは「防げない」と書く）。
3. 仮の repo（scratchpad 等）で `orgctl new`→`assign --persona` を打って、ペルソナと職種がシステムプロンプトに入ることを確かめた結果が報告にある。
4. 雛形の README（`org/README.md`）とプラン（`docs/todo/ai-org-plan.md` の「立場と職種」）に、足したものが書かれている。
