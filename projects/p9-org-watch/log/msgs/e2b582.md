**チーム `watch` を 1 つ。子プロジェクトは無し**（PM の見立てに同意）。ただし作業者は 2 人に分け、同じチームで**並べて**走らせる。監査チームを別に立てるのには反対。

- 理由: 2 つの仕事は同じ worktree（`/Users/maka343noshi/orca/workspaces/dev-tools/org-watch`）の同じファイル 4 つ（`orgctl.py`・`org/README.md`・`docs/todo/ai-org-plan.md`・org-project-new の `SKILL.md`）を触る。チームを分けると、ぶつかりの交通整理が PM まで上がる。リーダー 1 人なら、受け持ちの境目と共有の文書を書く順をチームの中で決められる。
- `orgctl.py` の同時編集は、関数ごとに分ければぶつからないと見ている（読んで確かめた範囲。見張りは 556〜790 行あたり、export は 1100〜1400 行あたりで離れている）。
  - `worker-watch`: 定数（`WAITING_SEC`・`STALL_MIN`・`LOOP_MIN`）・`cmd_wait`・`member_state`・`cmd_watch`・`patrol_once`・`cmd_patrol`・`main()` の引数
  - `worker-audit`: `_ProjectReader`（`audits` など）・`build_snapshot`・`cmd_export`・`teardown_*`・`org/schema/snapshot.schema.json`
  - `main()` に引数が要るときは `worker-audit` がリーダーに言い、`worker-watch` が足す。編集は 2 人とも Edit で差分だけ（ファイル全体の書き直しや整形はしない）。
- 共有の文書は節で分ける: org-project-new の 5 と README の見張りの節は `worker-watch`。7 と README の監査の節は `worker-audit`。
- 順番:
  1. 2 人が並べて始める。
  2. `worker-watch` が承認されたら、リーダーが `worker-audit` に、プランの決まったこと 22 の補足（元の文は残して併記）と、README・プランの通しの揃え（完了条件 5）を渡す。
  3. リーダーが PM へ報告する。
- つなぎ: チームの外とのつなぎは PM だけ。作業者どうしは直接やりとりせず、リーダーを通す。

  - **p8 の当時の状態を作り直せる。** p8 の `member.json`・`.waiting` は片づけで消えていて、残っているのは `log/.patrol.json` だけ（確かめた）。完了条件 2 は、`events.log` から 16:30 ごろの状態を scratchpad に作り直して確かめることになる。パックにそう書いた。

  - **p9 を閉じるとき、監査役に新しい立場が入る。** `assign` は orgctl が置かれた所の `org/positions/` を読む。本体の orgctl だと古い監査役（改訂案を出す形）が入る。p9 を閉じるときは、PM が worktree の orgctl（`/Users/maka343noshi/orca/workspaces/dev-tools/org-watch/org/scripts/orgctl.py`）で監査役を assign できる必要がある。`worker-audit` に、それができるかを確かめて手順に書かせる。
  - **orgctl のコードを直すだけで済む。** Orca の automation の定義は `orca automations create --help` で書き方が分かる（`orca automations` はある。確かめた）。登録はしない。

## 4. charter（`teams/watch/charter.md`）に入れてほしいこと

完了条件の要点（照らせる箇条）:

1. 全員待ちの形（全員が `wait` の中で、誰も相手に何も出していない。例: リーダーが配下の `done` を全部受けたのに PM へ `report` を出していない）を、patrol が止まりと判定し、`gchat-notify`（slug `ai-org`）と `log/user-inbox.yaml` に知らせる。本文から、誰が誰を待っていて、何が出ていないかが分かる。仮のプロジェクトで確かめ、試しの送信は「［試し］」付きで要る分だけ。
2. `watch` が、待っているだけのメンバーと、止まっている・ループしているメンバーを出し分ける。p8 の記録から作り直した 16:30 ごろの状態で、PM が「ループ?」と出ない。そのうえで、本当に止まった・ループしたメンバー（作った例）は今までどおり「止まっている?」「ループ?」と出る。
3. 開いている全プロジェクトを 1 回見て終わる形（例: `patrol --projects <dir> --once`）が CLI にある。Orca の automation の定義（コマンド・間隔・どの repo で動かすか）と登録までの手順が、org-project-new か README にある。org-project-new の 5 が、常駐に切り替わる前と後の扱いが分かる形になっている。登録はしない。
4. 閉じる手順（org-project-new の 7）に、監査役が動く段がある（誰が・いつ assign し、何を渡し、出力を待ってから teardown する）。監査役の立場（`org/positions/auditor/position.md`）の出力は「起きたこと（問題・課題）と参照元」で、直し方を含まない。出力の置き場が決まっていて、`orgctl export` の snapshot に載る。`export --check` が通り、p3 の前の形も読めたまま。p9 を閉じるときに worktree の orgctl で監査役を動かせることを確かめた結果がある。
5. `org/README.md` と、プランの決まったこと 22（とその補足）が新しい形に合っている。元の文は消さずに併記している。
6. dev-tools の本体と ai-org の `projects/` は書き換えていない。

つなぎ: PM から charter を受け、PM へ `report` を出す（全員の `done` を読んだらその場で）。チームの外とのつなぎはこれだけ。

閉じるときの監査役（p9 自身の監査）は PM の立場の仕事なので、パックは書いていない。必要なら言ってほしい（そのときは `packs/auditor.md` に書く）。
