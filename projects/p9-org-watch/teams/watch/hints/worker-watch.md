# ヒント（worker-watch）

## こう作ればいけると思う

- 「待っている」と「止まっている」を分けるのは、本人の状態ではなく **やりとりの向き**。各メンバーについて「最後に自分宛てに来たもの」と「最後に自分が出したもの」を events.log から取り、`.waiting` が新しい（wait の中）なら「待っている（誰の何を）」として、STALL・LOOP の判定から外す。ループ?・止まっている? は、wait の中にいない人だけに出す。
- 全員待ちは、コンポーネント（プロジェクト全体）単位で見る: 起きているメンバー全員が「wait の中」か「ターンを終えて止まっている（出力も心拍も一定時間無い）」で、かつ一定時間、誰も event を出していない。そのとき「誰が誰を待っているか」の一覧と、「出ていないもの」を本文にする。出ていないものの推定は、たとえば「リーダーが配下全員の done を受けたのに上へ report を出していない」「作業者が review_request を出したのにレビュアーが返していない」のように、最後のやりとりから「次に出るはずの種類と出す人」を引く形。
- 繰り返さないのは、詰まりの指紋（全員の最後の event の hash の組など）を patrol の state に持ち、同じ指紋なら出さない。誰かが動けば指紋が変わり、また詰まれば出してよい。
- 全プロジェクトを 1 回見る形は `patrol --projects <dir> --once`。閉じたプロジェクト（component.json の状態）は飛ばす。automation の定義は「この 1 行を何分おきに、どの repo で」を README か org-project-new に書く。

## 気をつけてほしい点

- 判定を緩めすぎない。本当に止まった人・ループした人（作った例）が今までどおり「止まっている?」「ループ?」と出ることも確かめる。
- p8 の確かめは、`events.log` から 16:30 ごろの member.json・`.waiting` を scratchpad に作り直す（「足場が残っていない」で止めない）。どう作り直したかを、レビュアーが同じ手順で再現できる形で報告に書く。
- `.waiting` を書かない（wait を打たずにターンを終えた）人が混じる全員待ちも拾うこと。
- 受け持ちの関数と `main()` の引数以外を触らない。`worker-audit` から `main()` の引数の依頼がリーダー経由で来たら足す。
- Google Chat への送信は確かめに要る分だけ、本文の頭に「［試し］」。それ以外は `--dry`。
