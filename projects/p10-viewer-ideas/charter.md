# 目的

AI 組織のビューア（ai-org の `viewer/`、http://localhost:4390 ）の改善点を洗い出し、川崎さんが「何を改善できるか・なぜか・どれからやるか」を把握できるレポートにまとめる。**実装はしない。** 川崎さんがレポートを読んで、どれを実装するかを決める（2026-10-24 川崎さん）。

いまのビューアは p8 で組織が作り直し、川崎さんが「わかりやすい。時系列と往復が分かりやすい」と判定した。そのうえで、もっと分かりやすくする点と、組織の改善に役立つ機能を探す。

材料（必ず読む）:

- いまのビューアの実物: http://localhost:4390 （ai-org の本体で動いている。画面は撮ってよい。止めない・再起動しない）、コードは ai-org の `viewer/`、データの形は dev-tools の `org/schema/snapshot.schema.json`
- p8 の記録: ai-org `projects/p8-viewer-rebuild/`（`teams/viewer/design.md`・PM の報告 `log/msgs/b20186.md` の「申し送り」「うまくいかなかったこと」）
- 川崎さんのフィードバック: job の `company/system/ai-org/feedback/2026-10-24-viewer.md`、ペルソナ: dev-tools の `org/personas/kawasaki.md`、UI の原則とチェックリスト: dev-tools の `org/common/ui/`
- 根っこのセッションが挙げた案（叩き台。採るかどうか・ほかに無いかは組織が決める）:
  1. 前回見てから何が変わったか（新しいプロジェクト・終わったもの・判断待ちの増減）を最初に見せる
  2. データの時刻を目立たせ、写しが古いときは警告する（古い写しで「動いている」と出て川崎さんが混乱した）
  3. 動いているプロジェクトで「いま誰が誰を待っているか」を見せる（p8 の全員待ちが画面で一目で分かる）
  4. プロジェクトの画面から成果物（出した PR・マージされたか・変わったファイル）へつなぐ
  5. 完了条件ごとの「通ったか」と根拠（報告・撮った画面）へのリンク
  6. 人（根っこ・川崎さん）が手を入れた回数を、図の別の印で数える（組織の自律の度合い）
  7. 「直し待ち」の課題の画面（問題と参照元だけ。同じ問題の回数、unclear の似たものをまとめて頻度順）
  8. プロジェクトをまたいだ推移（時間・トークン・差し戻し・人の介入を p1 からの線で）
- 外のリサーチ: 似た道具（マルチエージェントの観測・トレースのビューア、CI のダッシュボード、分散トレースの UI など）が何を見せているか。Web 検索は dev-tools の `gemini-api` を使ってよい。

# 完了条件

1. レポート `report.md` がこのプロジェクトの直下にある。冒頭に Summary（川崎さんが 1 分で掴める要点）と、推奨する上位 3〜5 件。
2. 改善案ごとに、次がそろっている: 何に困る（または何が分からない）からか＝**記録に根拠がある問題**（どのプロジェクトの何の記録か）、見せ方の案、川崎さんにとっての価値、作る重さ（データの足し・画面の足し・orgctl の変更の有無）、優先度とその理由。根拠を示せない案は「根拠なし（推測）」と明記する。
3. 叩き台の 8 件それぞれについて、採る・採らない・形を変える、とその理由がある。叩き台に無い案も探して入れている。
4. 外のリサーチから取り入れた考え方が、出典付きで入っている。
5. 見せ方の案には、いまの画面を撮った画像（どこを変えるか）を添える。新しい画面の絵は必須ではない（実装しないので、作り込まない）。
6. 川崎さんのペルソナ（`kawasaki`）の目線で、レポートそのものが「長すぎず、要点から先に、開いて回らずに掴める」かをレビュアーが確かめている。

# 範囲

- 書いてよい場所: このプロジェクトのディレクトリ（`projects/p10-viewer-ideas/`）の中だけ。ai-org の `viewer/`・dev-tools・job は読むだけ。**コードは変えない。**
- 4390 番のビューアは見るだけ（止めない・再起動しない）。手元で別に立てる必要があれば 4391〜4399 番を使い、終わったら止める。ローカルのポートの待ち受けと Playwright はサンドボックスの外で動かす（dev-tools の `org/common/screen-check.md`）。
- 監査の指摘と unclear の一覧づくりは、別のプロジェクト（p11）が並行してやる。こちらは「その一覧をビューアでどう見せるか」までに留める。
- git の操作はしない。
- うまくいかなかったことは、隠さずセッション報告の `unclear` と最後の報告に書く。
