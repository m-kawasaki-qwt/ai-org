# worker-1 へのヒント

## 方向

- 読み手は川崎さん 1 人。1 枚開いて「誰が・いつ・誰に・何を出したか」と「各セッションの時間とトークン」が掴めればよい。凝った操作より、開いた瞬間に流れが見えることを優先する。
- 形の案: 横軸が時刻、縦にメンバーの帯（`<div>` か `<svg>` を Python で直接組み立てる）。各報告は送り手の帯に置いた小さな印（種類ごとに色＋短いラベル）。本文は `<details><summary>` で折りたたむと JS 無しで読める。帯の頭（左端）に、そのメンバーの span_min・tokens_total を出すと 1 枚で済む。
- 時刻の間隔が偏る（数秒に何件も並ぶ・十数分空く）ので、厳密な比例配置だと重なる。時刻順の列（1 件 1 列）にして、列の上に時刻を書く方が読みやすいかもしれない。どちらにするかは任せる。
- HTML は `html.escape` を通す。本文の md はそのまま `<pre>` でよい（md の描画はしなくてよい）。

## 気をつけてほしい点

- `events.log` には、人の報告以外の行（`assign` `launch` `notify_sent` `notify_recv` `ack` `teardown` `component_new` など）も入っている。宛先が `-` の行もある。全部出すと読めなくなるので、出すもの・まとめるもの・落とすものを決めること（ただし完了条件 3 の種類は必ず出す）。決めたことは報告に書く。
- 子のチームの `component.json`（`teams/*/component.json`）にもメンバーがいる。帯の並びは、組織の上から（user → PM → リーダー → 作業者・レビュアー）にすると読みやすい。
- セッション報告のファイル名には、末尾にハッシュが付くもの（p2）と付かないもの（p1）がある。メンバーの id は中の `machine.id` で取る。YAML は自前で読む（`machine:` の下の `span_min` `tokens_total` など、必要な項目だけ）。
- p1・p2 の実データで両方動かして、ブラウザで開いて見ること（目で見て読めるか）。テストは作り物の fixture で。既存の `tools/tests/test_org_status.py` を壊さない。
- 書いてよい場所は charter の「範囲」のとおり。
