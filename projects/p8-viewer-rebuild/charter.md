# 完了条件

1. **画面ごとに「何のために、何を判断するために出すか」が先に決まっている。** UI デザイナーが `design.md`（checklist の B への答え）を書き、画面と、画面の中の要素ごとに目的を書いている。一覧に載せる列は一つ一つ「なぜ詳細ではなく一覧に載せるのか」の理由がある。目的を言えない画面・要素は載せない（パフォーマンス・監査の画面も、何を判断する画面かを言えなければ作り直すか外す）。
2. **フィードバックの指摘が一つ残らず潰れている。** 指摘ごとに「どの画面のどの要素で、どう直したか（または、なぜ外したか）」の対応表が報告にある。最低限: ダークモード、900〜1800px で崩れない、一覧の概要は 10 文字程度、表が改行で崩れない、Markdown は整形して出す、クリックできるものが見て分かる（ポインタ・見た目）。
3. **時系列は「構造」が見える図になっている。** メンバーごとの帯に時刻順で並べ、誰から誰へのやりとりが線で分かり、入れ子（プロジェクト → チーム → メンバー）が分かる。ログを縦に並べただけの表示は主役にしない。p6・p7 のように、コーディネーターとの往復・レビューの差し戻し・リーダーの入れ替えがあったプロジェクトで、その流れが図から読める。
4. **川崎さんの目線で撮って確かめてある。** 900px と 1800px の両方で、全画面を Playwright で撮り、`kawasaki` のペルソナのレビュアーが「判定の問い」と checklist の C に照らして合格を出している。PM も撮った画像を自分で開いて見てから上げる。報告に、撮った画像のパスと判定を書く。
5. 実データで動く。ai-org の `projects/` の p1〜p7（と、このプロジェクト自身）を `orgctl export` で書き出した `snapshot.json` で表示が崩れない。`snapshot.json` に足りない項目があれば、`orgctl export` とスキーマ（`org/schema/snapshot.schema.json`）を直す。
