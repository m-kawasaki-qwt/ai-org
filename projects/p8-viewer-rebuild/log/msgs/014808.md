## 1. 切り方・つなぎ方・順番

**チーム 1 つ `viewer`（子プロジェクトにしない）。PM の案に同意する。** 画面どうしと、画面が要る snapshot の項目が密につながっていて、分けるとつなぎ（何を足すか）がチームをまたぐ往復になるため。

PM の案から 1 点変える: **作業者を「UI デザイナー＝決める人／エンジニア＝組み立てる人」ではなく、repo で分ける。**

- `worker-ui`（UI デザイナー）が `design.md` も **Astro の組み立てと撮影も** 持つ。workdir は ai-org の worktree。
- `worker-export`（エンジニア）は orgctl の export とスキーマだけを持つ。workdir は dev-tools の worktree。
- 理由: 決める人と組み立てる人を分けると、`design.md` の意図が組み立てで落ちる（p5 の「記録の形から画面を作る」に戻る筋）。職種 `ui-designer` の規範も「組み立てるとき」「出す前に自分で撮る」まで持っている。repo で分ければ、1 人が 2 つの repo を触る権限・パスの前提（PM の挙げた崩れそうな点）も消える。

つなぎ（チームの中）:

- `worker-ui` → リーダー: `design.md` の「snapshot に要るもの」の節
- リーダー → `worker-export`: 上の節を `start` で渡す（作業者どうしは直接やりとりしない）
- `worker-export` → `A/viewer/data/snapshot.json`（書き出し）→ `worker-ui` が実データで組み立てる

順番:

1. 並べる: `worker-ui` が `design.md` を書く ∥ `worker-export` が今の snapshot で p1〜p8 を書き出して `--check`、足りなそうな項目を洗い出す（直さない）。
2. `reviewer-kawasaki` が `design.md` を B に照らして通す。**通るまで画面を組み立てない。**
3. リーダーが「snapshot に要るもの」を `worker-export` へ → 直す → `reviewer-export` が通す。
4. `worker-ui` が実データで組み立て、撮って `reviewer-kawasaki` へ → リーダーが撮り直して判定 → PM。

## 3. 実現できる理由と崩れる前提

実現できる理由:

- snapshot はすでに `Event` に `from`・`to`・`component`・`kind`、`tree` に入れ子の `Component`・`Member` を持つ。時系列の図（帯・線・入れ子）の材料の大半はあり、export は追加で済む見込み。
- 記録の量はプロジェクトあたり最大 207 行（p6、ack・notify を含む）で、図で読める範囲。
- 1 人 1 repo なので、workdir と書いてよい場所が 1 対 1 に揃う。

崩れる前提（外れたら切り直す）:

- export の追加で足りる（既存の関数の振る舞いを変えずに済む）。変える必要が出たら、orgctl を使う他のプロジェクトへの影響の判断が要るので PM へ上げる。
- `worker-ui` が別の worktree の `D` の orgctl を読んで export を打てる（ai-org の worktree を workdir にしても `~/orca` の下は読める前提）。
- `worker-export` が ai-org の worktree の `viewer/data/snapshot.json` に書ける（サンドボックスの書き込みは `~/orca` の下が許されている）。
- 待ち受けと Playwright をサンドボックスの外で動かせる（p5・p6 では動いた）。
