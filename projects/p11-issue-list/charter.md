# 目的

AI 組織で「起きた問題・課題」を一覧にし、川崎さんがどれから直すかを選べるようにする。材料は、これまでのプロジェクト（閉じている p1〜p9）の記録に散らばっている。

- セッション報告の `unclear`・`not_done`（ai-org `projects/*/reports/sessions/*.yaml`。ビューアの「決まりの直し候補」で 111 件以上）
- 監査役の出力（p3 の改訂案 `projects/p3-org-visibility/log/msgs/`、p9 の `projects/p9-org-watch/reports/audit/p9-org-watch.md`）
- PM・リーダーの報告の「うまくいかなかったこと」（`projects/*/log/msgs/`）
- 根っこのセッションの控え: job の `company/system/ai-org/README.md` の「組織の直し待ち」

**書くのは起きたこと（問題・課題）と参照元だけ。直し方は書かない**（直し方は着手の直前に、そのときのモデル・組織・アイデアで考える。dev-tools の `docs/todo/ai-org-plan.md` の決定ログ 2026-10-24「問題だけを控え、直し方は着手の直前に考える」）。

# 完了条件

1. 一覧 `issues.md` がこのプロジェクトの直下にある。冒頭に Summary（件数・多い分類・何度も起きているもの上位）。
2. 同じ問題をまとめて 1 件にしている（言い方が違っても中身が同じものは 1 件）。1 件ごとに: 題（1 行）・起きたこと（事実だけ）・回数（何プロジェクトで何回）・参照元（ファイルと行、または 1 行報告の hash を全部）・分類（例: 連絡・見張り・規範の書き方・道具・文脈パック・レビュー・人の操作）。
3. 並びは回数の多い順。同数なら新しい順。
4. もう直ったもの（あとのプロジェクトで雛形や orgctl が変わり、起きなくなったもの）は「直った」の印と、直した記録（PR・プロジェクト）を付けて残す（消さない）。直ったかどうか判断できないものは「不明」。
5. 直し方・改訂案・「こうすべき」を書いていないことを、レビュアーが全件で確かめている。
6. 参照元が実在する（ファイルと行が合っている）ことを、レビュアーが抜き取り（10 件以上）で確かめている。
7. 一覧の作り方（どこを読んだか・まとめ方の基準）が `issues.md` の末尾に数行ある（次に作り直すときに同じやり方で作れるように）。

# 範囲

- 書いてよい場所: このプロジェクトのディレクトリ（`projects/p11-issue-list/`）の中だけ。ほかのプロジェクトの記録・dev-tools・job は読むだけ。
- 数（件数・回数）はスクリプトで数える（暗算しない）。数えたスクリプトはこのプロジェクトの中に残す。
- ビューアでの見せ方は、別のプロジェクト（p10）が並行して考えている。こちらは一覧の中身まで。
- 動いている p10 の記録は材料に含めない（閉じていないので）。
- git の操作はしない。
- うまくいかなかったことは、隠さずセッション報告の `unclear` と最後の報告に書く。
