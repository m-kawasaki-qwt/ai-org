# 目的

AI 組織で起きた問題・課題を一覧（`issues.md`）にまとめ、川崎さんがどれから直すかを選べるようにする。プロジェクト p11-issue-list の成果物そのもの（プロジェクトの charter: `/Users/maka343noshi/ghq/github.com.qwt/m-kawasaki-qwt/ai-org/projects/p11-issue-list/charter.md`）。

材料（閉じている p1〜p9 だけ。p10 は読まない）:
- セッション報告の `unclear`・`not_done`（`projects/p1〜p9/**/reports/sessions/*.yaml`）
- 監査役の出力（`projects/p3-org-visibility/log/msgs/` の改訂案、`projects/p9-org-watch/reports/audit/p9-org-watch.md`）
- PM・リーダーの報告の「うまくいかなかったこと」、`review_ng`・`rework`・`blocked`・`escalate` の本文（`projects/*/log/msgs/`、`events.log`）
- job の `company/system/ai-org/README.md` の「組織の直し待ち」（読むだけ）
- 「直った」の判断材料: dev-tools の `org/`・`docs/todo/ai-org-plan.md` の決定ログ、dev-tools と ai-org の git log（読むだけ）

**書くのは起きたこと（問題・課題）と参照元だけ。直し方・改訂案・「こうすべき」は書かない。**

# 完了条件

1. 一覧 `projects/p11-issue-list/issues.md` がある。冒頭に Summary（件数・多い分類・何度も起きているもの上位）。
2. 同じ問題をまとめて 1 件にしている（言い方が違っても中身が同じものは 1 件）。1 件ごとに: 題（1 行）・起きたこと（事実だけ）・回数・参照元（ファイルと行、または 1 行報告の hash を全部）・分類（例: 連絡・見張り・規範の書き方・道具・文脈パック・レビュー・人の操作）。
3. 回数は「何プロジェクトで」と「記録の数」を分けて出す。並びは回数の多い順、同数なら新しい順。どちらの回数で並べたかを作り方に書く。同じ件を別の出どころ（job の控えなど）が書いたものは参照元に足すが、二重に数えない。
4. 状態は 3 つ:「直った」（直した記録＝main にマージ済みの PR・コミット・プロジェクト **かつ** その後のプロジェクトで再発なし。根拠を 1 行）／「不明」（何が足りないかを 1 行）／印なし（まだ起きている）。直ったものも消さずに残す。
5. 直し方・改訂案・「こうすべき」を書いていないことを、レビュアーが全件で確かめている。
6. 参照元が実在する（ファイルと行が合っている）ことを、レビュアーが乱数で選んだ 10 件以上の抜き取りで確かめ、乱数の種を `review_ok` に書いている。
7. 数（件数・回数）はスクリプトで数え、スクリプトを `projects/p11-issue-list/scripts/` に残している。レビュアーがスクリプトを回して数が合うことを確かめている。
8. 中間の確かめ: 抜き出しの中間ファイル（1 行 1 件・参照元つき）と、材料ごとの件数表（0 件ならその理由）がある。まとめに入る前に、レビュアーが網羅を承認している（この網羅の段の往復は、本体のレビューの指摘回数の上限とは別に数える）。
9. 中間ファイルの各行が `issues.md` のどの件に入ったか（または入れなかった理由）の対応表がある。
10. 一覧の作り方（どこを読んだか・まとめ方の基準・並びに使った回数）が `issues.md` の末尾に数行ある。
11. リーダーが回数の上位 5 件を原文まで辿って確かめ、結果を PM への報告に書いている。
