# 目的

チームコーディネーターの役割を改める。いまは「PM がチーム・子プロジェクトを作ったあとに、そのコンポーネントのためだけに 1 回呼ぶ」形で、p6 ではチームの数だけコーディネーターが 2 人立ち、チーム同士のつなぎ（どこで分けるか・何を渡し合うか・どの順か）を誰も持っていなかった。

これを次の形にする（プランの決定ログ 2026-10-24 の最後の行。dev-tools の `docs/todo/ai-org-plan.md`）。

1. PM は、目的とおおまかな考え（「こういうことを実現したい・こう組めばいいと思うがどう思う？」）を、コンポーネントを作る**前に**コーディネーターへ相談する。
2. コーディネーターはチームの切り方（いくつに分けるか・チームか子プロジェクトか・つなぎ方・順番）まで責任を持ち、「この編成なら実現できる」を、編成案と一人ずつの文脈パック付きで返す。
3. PM は返ってきた案に視点を足して相談し、往復して合意してから、コンポーネントを作り、メンバーをアサインする。
4. だから 1 つの相談にコーディネーターは 1 人。

川崎さんの言葉（原文）:

> そもそもプロジェクトマネージャーがもちろん案として出すのはいいんだけど…チームコーディネーターがそこに責任を持って、こういうチームであれば実現できると思いますよって返すのがチームコーディネーターの役割…だからコーディネーターが二人立つってことは基本的にないと思う…相談してやってもらうのが前提かなと思う

# 完了条件

1. コーディネーターの規範（`org/positions/coordinator/position.md`）が、上の 1〜4 の流れになっている。返すもの（編成案に、切り方・つなぎ方・順番とその理由が入る）、往復のしかた（PM の相談に返す・PM の視点を受けて直す・合意したら終わる）、責任の範囲が書かれている。
2. PM の規範（`org/positions/pm/position.md`）と、チームの作り方のスキル（`org/positions/pm/skills/org-team-setup/SKILL.md`）が、「先に相談 → 往復して合意 → 作る」の順になっている。コンポーネントごとにコーディネーターを立てる手順（`coordinator-<チーム名>`）が無くなっている。決定ログの「決まったこと 16 を改める」に合わせて、プランの「決まったこと」16 にも改めた内容を併記している（元の文は消さず、改めたことが分かる形に）。
3. 文脈パックの置き場（いまは作るコンポーネントの `packs/`）が、先に相談する流れでも成り立つ。コンポーネントがまだ無い時点でパックをどこに書き、作ったあとどう渡すかが決まっていて、`orgctl`（`assign --pack` など）がその形で動く。直す必要がなければ、そう判断した理由が報告にある。
4. 仮の repo（scratchpad 等）で `orgctl new` → コーディネーターの assign → 相談の往復を模した event → 合意後にチームを作って `assign --pack` までを打ち、新しい流れが CLI で通ることを確かめた結果が報告にある。
5. 雛形の README（`org/README.md`）とプランの「立場と職種」の記述が、新しい流れに合っている。
